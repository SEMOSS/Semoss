# Platform SDK: app bootstrap

`@semoss/sdk` is the client library an app uses to talk to the platform server. Everything it does
runs through **Pixel**, the server's command language, and every Pixel call runs **inside an
insight**. An insight is a server-side workspace: it holds the project context, the loaded
reactors, the Python process, the uploaded files, and the frame state.

The single most important thing to get right when building an app from scratch is that **the base
insight must exist and be bound to the project before any request goes out**. Everything else in
this file follows from that.

**The SDK core is framework-agnostic.** `@semoss/sdk` is plain TypeScript with no React
dependency; React is a peer dependency and it is optional. Everything an app needs - insight
lifecycle, pixels, auth, uploads, websockets - is on the core entry. `@semoss/sdk/react` adds a
provider and hooks that wrap that same core and nothing else. Build without React unless the app
already uses it.

| Import | Needs React | Contents |
| --- | --- | --- |
| `@semoss/sdk` | no | `Insight`, `Env`, `runPixel`, auth, uploads, websocket, utilities |
| `@semoss/sdk/react` | yes | all of the above, plus `InsightProvider` and the hooks |

For what a given pixel does and returns, use the task skills: `database`, `model`, `vector`,
`room`, `agent-run`, `file-uploads`. For compiling and publishing, use `build-and-publish`.

## Project layout

A platform app is a project folder. The parts that matter:

```
<project>/app_root/version/assets/
  client/                  source you edit (omit entirely for a no-build HTML app)
    .env                   committed defaults (ENDPOINT, MODULE)
    .env.local             local only, never committed (APP, VITE_ACCESS_KEY, VITE_SECRET_KEY)
    vite.config.ts         root: "src", build.outDir: "../../portals"
    src/
      index.html           entry html - do NOT put a semoss-env tag here
  portals/                 build output - this is what the server publishes and serves
  mcp/pixel_mcp.json       optional, only if the app exposes MCP tools
```

`client/src` is the build root and `portals/` is the output. Never hand-edit `portals/`: it is
regenerated by every build. A no-build HTML app skips `client/` and lives directly in `portals/`.

Build and publish with the `BuildAndPublishApp` tool, or `PublishProject` for an app that needs
no compilation. Never `npm`/`pnpm`/`node` via Bash. See the `build-and-publish` skill.

## The base insight

`initialize()` is the whole bootstrap. It runs these steps in order, and each one can leave the
app dead in a different way, so know what they are:

1. **Read the environment from the page.** Parses the JSON inside
   `<script id="semoss-env" type="application/json">` and calls `Env.update({ APP, MODULE })`.
   The tag only exists in a published build; in dev the parse throws and is swallowed, leaving
   whatever `Env.update()` set at module load.
2. **Require a MODULE.** No `Env.MODULE` means `Error("module is required")` and nothing else
   runs. This is the number one cause of a permanently blank app.
3. **Fetch the system config** from `GET {MODULE}/api/config`. This populates `system.config`
   (logins, availableProviders, theme, systemDate) and captures the CSRF token used by every
   later POST. On success `isInitialized` becomes true.
4. **Decide authorization.** The user is authorized when `system.config.logins` is non-empty, or
   when `Env.ACCESS_KEY` and `Env.SECRET_KEY` are both set (dev). If not authorized, the sequence
   stops here: `isAuthorized` stays false, no insight is created, and `initialize()` returns
   `null`.
5. **Create the insight.** Runs a setup pixel and stores the returned `insightID`:
   - `SetContext("<appId>");` when an app id is known, otherwise the no-op `META | init`
   - plus `WriteObjectToFile(...) ; LoadPyFromFile(...)` when a `python` option was passed
   - then `SetRoomForInsight(roomId=...)` when the app is running as an MCP tool in a room
   Finally `isReady` becomes true and `initialize()` resolves to `{ tool }`.

**`SetContext` is what makes requests valid.** It binds the fresh insight to the project so the
project's reactors, asset folder, working directory, and MCP tools resolve. An insight created
without it still runs generic pixels such as `1 + 1` or `MyEngines(...)`, which is exactly why
this bug hides: the smoke test passes and everything project-scoped fails.

The app id reaches `SetContext` from `Env.APP`, which comes from the `semoss-env` tag in
production and from `.env.local` in dev. If neither is set, the insight is created contextless.

### Bootstrap, no framework

```ts
import { Insight } from "@semoss/sdk";

const insight = new Insight();

// initialize resolves to { tool } when it got all the way through, null otherwise
const result = await insight.initialize();

if (insight.error) throw insight.error;                    // step 2 or 3 failed
if (!insight.isAuthorized) return showLogin(insight);      // step 4 stopped it
if (!insight.isReady) throw new Error("insight not ready"); // step 5 failed

const insightId = insight.insightId;
```

`insightId` is a public getter. Do not reach into `insight._store` - it is private and its shape
is not part of the public API.

`initialize()` accepts `{ app?, python?, disableRoom?, insightId? }`. Pass `insightId` to attach
to an insight that already exists; the SDK then skips the setup pixel instead of resetting the
frame out from under whoever owns it.

### The flags are the state machine

There is no framework needed to gate on them - they are three booleans read in order:

| Flag | True when | Gate |
| --- | --- | --- |
| `isInitialized` | `/api/config` came back | show the app shell; before this, a loading state |
| `isAuthorized` | a session exists (or dev keys are set) | show protected UI; otherwise the login form |
| `isReady` | the insight exists and is bound | run any pixel |

A vanilla gate is a single function:

```ts
const render = () => {
  if (insight.error) return renderError(insight.error);
  if (!insight.isInitialized) return renderLoading();
  if (!insight.isAuthorized) return renderLogin();
  if (!insight.isReady) return renderLoading();
  return renderApp();
};
```

Call it after `initialize()`, after login, and after logout. That is the entire job
`InsightProvider` does in React.

### The same thing with React

```tsx
import { InsightProvider, useInsight } from "@semoss/sdk/react";

const App = () => (
  <InsightProvider>
    <Gate />
  </InsightProvider>
);

const Gate = () => {
  const { isInitialized, isAuthorized, isReady, error } = useInsight();
  if (error) return <ErrorScreen error={error} />;
  if (!isInitialized || (isAuthorized && !isReady)) return <LoadingScreen />;
  if (!isAuthorized) return <LoginPage />;
  return <Home />;
};
```

`InsightProvider` creates one `Insight`, calls `initialize()` in an effect, and copies the
getters into state after every action. Notes:

- Its `options` prop is compared by `JSON.stringify`, so an inline object literal is safe.
- `destroyOnUnmount` defaults to true. Under React 18 StrictMode the dev double-mount will create
  an insight, drop it, and create another. Expected in dev, not a bug to chase.
- Mount exactly one `InsightProvider`. One insight per session, in any framework.

## Running pixels

Three entry points. Only the third needs React:

| From | Call | Errors |
| --- | --- | --- |
| anywhere (module scope, utilities, plain HTML) | `runPixel(pixel, insightId)` | returned in `errors[]` |
| an `Insight` instance | `insight.actions.run(pixel)` | thrown |
| a React component | `usePixel<D>(pixel)` | in `status` / `error` |

`runPixel` and `actions.run` return the same envelope:

```ts
{
  errors: string[];            // non-empty means the pixel did not execute
  insightId: string;
  pixelReturn: Array<{
    pixelId: string;
    pixelExpression: string;   // what the server actually parsed - read this when debugging encoding
    isMeta: boolean;
    timeToRun: number;
    operationType: string[];   // ["OPERATION"], ["ERROR"], ["MCP_TOOL_EXECUTION"], ...
    output: unknown;           // shape is pixel-specific
  }>;
}
```

One `pixelReturn` entry per `;`-separated statement. Type it with a tuple:

```ts
const { errors, pixelReturn } = await runPixel<[Array<{ engine_id: string }>]>(
  `MyEngines(engineTypes=["MODEL"], limit=[50], offset=[0]);`,
  insightId,
);
if (errors.length) throw new Error(errors[0]);
const models = pixelReturn[0].output;
```

`runPixel` also sends the browser timezone as `tz`, so server-side date handling matches the
user.

### The bug to design against: a pixel with no insight id

`runPixel(pixel)` without an `insightId` does not fail. The server mints a **brand new,
contextless insight** for that one call. Symptoms:

- generic pixels work, project-scoped ones do not
- every call is slow, because each one pays insight creation
- server-side insights pile up and are never dropped
- state set by one call is invisible to the next

So: **always pass `insightId`, and only call once `isReady` is true.** `insight.actions.run`
does this for you, which is the main reason to prefer it over the bare `runPixel`. In React,
`usePixel` falls back to the context `insightId`, which is the empty string until the insight
exists, so a `usePixel` mounted above the gate hits exactly this path.

### One wrapper, used everywhere

Centralize the envelope handling once rather than repeating it. No framework required:

```ts
export const createPixelRunner = (insight: Insight) => {
  return async <T>(pixel: string): Promise<T> => {
    const { errors, pixelReturn } = await runPixel<[T]>(pixel, insight.insightId);
    if (errors.length) {
      throw new Error(errors.join(", "));
    }
    return pixelReturn[0].output;
  };
};
```

Never swallow the error. An empty `catch` here is the single most common reason a finished app
renders empty cards and `--` with a clean console.

### "No response" means unauthorized

`insight.actions.run` routes failures through an internal handler that **swallows**
`UnauthorizedError` (a 302 or a redirect header), flips `isAuthorized` to false, and then falls
through to `throw new Error("No response")`. So a thrown `"No response"` is not a network
glitch - it means the session died. Re-check `insight.isAuthorized` and send the user back to
the login gate rather than retrying.

## Env: dev vs published

| Key | Dev | Published |
| --- | --- | --- |
| `MODULE` | `client/.env` -> `MODULE="/Monolith"`, the dev server proxies it to `ENDPOINT` | injected by the server into `semoss-env` |
| `APP` | `client/.env.local` -> `APP="<project-id>"` | injected by the server into `semoss-env` |
| `ACCESS_KEY` / `SECRET_KEY` | `client/.env.local` -> `VITE_ACCESS_KEY` / `VITE_SECRET_KEY` | absent, cookie session instead |

Access keys are sent as HTTP basic auth. Because basic auth is not cookie-based it is not
CSRF-forgeable, so the SDK skips the CSRF handshake entirely when both keys are set. That is a
dev-only path: never ship the keys.

The `semoss-env` tag is written into `portals/index.html` by the server on publish, as the first
child of `<head>`:

```html
<script id="semoss-env" type="application/json">{"APP": "<project-id>","MODULE": "/Monolith"}</script>
```

Do not add that tag to your source `index.html` by hand. A hardcoded app id is wrong the moment
the project is cloned or promoted to another server.

### Embedded in an iframe

If the app is embedded and the host passes auth by `postMessage`, the SDK does **not** wire this
up for you. Await it before `initialize()`, or the first request goes out unauthenticated:

```ts
import { Insight, waitForEmbedAuth } from "@semoss/sdk";

await waitForEmbedAuth(); // resolves immediately unless embedded with SMSS_EMBED_AUTH=true

const insight = new Insight();
await insight.initialize();
```

`waitForEmbedAuth` only waits when the page is in an iframe **and** `SMSS_EMBED_AUTH=true` is in
the query string or the hash query. It announces itself to the parent, waits up to 4 seconds for
a `SMSS_EMBED_AUTH` message, stores the bearer token on `Env`, and resolves either way. Calling
it unconditionally at startup is safe and is the right default for an app that may be embedded.

## Auth

```ts
await insight.actions.login({ type: "native", username, password });
await insight.actions.login({ type: "ldap", username, password });
await insight.actions.login({ type: "oauth", provider: "ms" });

// linotp is two steps: request the challenge, then confirm it
await insight.actions.requestOTP(username, pin);
await insight.actions.login({ type: "linotp", otp });

await insight.actions.logout();
```

Prefer `insight.actions.login` over the bare `login`/`loginLDAP`/`oauth` functions: the action
re-runs the insight setup on success, so `insightId` is repopulated and `isReady` flips back to
true. The bare functions authenticate and stop there, leaving you authorized with no insight.

`logout()` clears the stored CSRF token and resets `insightId`, so the next login builds a fresh
insight. Do not cache `insightId` outside the SDK across a login boundary.

`oauth` opens a popup on `window.top` and polls it once a second until it lands back on your
origin, so it must be triggered by a user gesture or the browser will block it.

The logged-in user's name is not on the insight. Read it from the config:

```ts
import { getSystemConfig } from "@semoss/sdk";

const config = await getSystemConfig();
const name = Object.values(config?.logins ?? {})[0]?.toString() ?? null;
```

`insight.system.config.logins` holds the same value on an already-initialized insight, which is
what to read on first paint. `system.config.availableProviders` lists the login options to
render.

## Files

Uploads are plain `FormData` posts. **The return shapes are not consistent - this is a trap:**

```ts
// returns the array directly
const files = await insight.actions.upload(fileOrFiles, path);

// returns the fetch envelope - the array is on .data
const { data } = await insight.actions.uploadInsight(path, fileOrFiles);
```

`upload` is deprecated and takes `(files, path)`. The newer `uploadInsight`, `uploadApp`,
`uploadEngine`, and `uploadUser` all take path-before-files and all return `{ response, data }`.
A request URL containing `path=[object File]` means the argument order was wrong.

Never set `Content-Type` by hand on an upload. The SDK's `post` deliberately leaves the header
off for `FormData` so the browser can generate the multipart boundary; setting it breaks the
upload.

`insight.actions.download(path)` runs `DownloadAsset` to get a file key, then triggers the
browser download. In a browser it fakes an anchor click and resolves as soon as the click is
dispatched - it does **not** wait for the bytes, so do not chain cleanup off it.

For attaching files to a model prompt, see the `file-uploads` skill.

## Streaming

For token-by-token output, submit asynchronously and poll. No framework needed:

```ts
import { runPixelAsync, getPixelJobStreaming } from "@semoss/sdk";

const { jobId } = await runPixelAsync(pixel, insight.insightId);

let done = false;
while (!done) {
  const { message, status } = await getPixelJobStreaming(jobId);
  for (const chunk of message) {
    if (chunk.stream_type === "content") appendText(chunk.data.content ?? "");
    if (chunk.stream_type === "thinking") appendThinking(chunk.data.thinking ?? "");
    if (chunk.stream_type === "tool") appendToolCall(chunk.data);
    if (chunk.data.finish_reason) done = true;
  }
  if (status === "Complete" || status === "Error" || status === "Canceled") done = true;
  if (!done) await new Promise((r) => setTimeout(r, 250));
}
```

`partial(insightId)` is the older single-string equivalent and is deprecated; use
`getPixelJobStreaming`. For durable multi-turn agent runs, use the `agent-run` skill instead -
it has its own subscription API.

### Websockets

`InsightWebSocket` is a framework-agnostic class - it is not a React hook and does not need one:

```ts
import { InsightWebSocket } from "@semoss/sdk";

const ws = new InsightWebSocket(insight.insightId, {
  onMessage: (data) => console.log(data),
  onStatusChange: (status) => console.log(status), // connecting | connected | disconnected
});

ws.connect();
ws.send(`GetSystemConfig();`);      // run a pixel over the socket
ws.watch("claude_code", { roomId }); // start a backend streamer
ws.unwatch("claude_code", { roomId });
ws.close();
```

It reconnects automatically with exponential backoff capped at 30 seconds, up to 5 attempts by
default; `close()` opts out permanently. `send`/`watch`/`unwatch` throw if the socket is not
open, so check `ws.isConnected` first. The React `useWebSocket(insightId)` hook is a thin wrapper
over this exact class.

## Python and MCP

```ts
// run python in the insight's python process
const { output } = await insight.actions.runPy(`smss.sayHello("world")`);

// preload python at bootstrap instead of shipping it in every call
await insight.initialize({
  python: { type: "script", script: pySource, alias: "smss" },
  // or { type: "file", path: "./hello.py", alias: "smss" }
});
```

When the app is opened as an MCP tool from the playground, the host posts a `SMSS_INIT_TOOL`
message. The SDK installs that listener on import and stores the result on `Env.TOOL`:

```ts
import { Env } from "@semoss/sdk";

if (Env.TOOL?.name === "my_tool") {
  const result = await doWork(Env.TOOL.parameters);
  insight.actions.sendMCPResponseToPlayground(JSON.stringify(result));
}
```

React apps get the same object as `tool` from `useInsight()`. When `Env.TOOL.roomId` is present,
`initialize()` also runs `SetRoomForInsight` so the insight writes into that room; pass
`disableRoom: true` to opt out. `sendMCPResponseToPlayground` throws outside an embedded browser,
so guard it on `Env.TOOL` being set.

## Cleanup

`insight.destroy()` runs `DropInsight()` and clears the state. `InsightProvider` does this on
unmount by default. A vanilla app should call it on `beforeunload`; scripts and tests should call
it when they finish.

## Bootstrap checklist

1. `client/.env` has `ENDPOINT` and `MODULE`; `client/.env.local` has `APP` and the dev keys.
2. `Env.update(...)` runs once at module scope, before anything constructs an `Insight`.
3. `await waitForEmbedAuth()` before `initialize()` if the app can be embedded.
4. Exactly one `Insight` for the session.
5. Source `index.html` has no `semoss-env` tag.
6. Nothing renders before `isInitialized`, nothing protected before `isAuthorized`, no pixel runs
   before `isReady`.
7. Every pixel call goes through one wrapper that passes `insightId` and checks `errors`.
8. Build with `BuildAndPublishApp`, or `PublishProject` for a no-build app.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| Blank screen, `module is required` | `Env.MODULE` empty: missing `MODULE` in `client/.env`, or the published `index.html` lost its `semoss-env` tag |
| `Error("No response")` from `actions.run` | the session died; `UnauthorizedError` was swallowed and `isAuthorized` is now false |
| Login page never clears after a correct password | logged in with the bare `login()` instead of `actions.login()`, so no insight was created |
| Generic pixels work, project pixels do not | insight created without `SetContext`: `Env.APP` was empty, or the call ran with no `insightId` |
| Every call is slow and state never persists | `runPixel` called without `insightId`, so each call creates a throwaway insight |
| `uploaded.map is not a function` | `uploadInsight`/`uploadApp`/`uploadEngine`/`uploadUser` return `{ response, data }`, not the array |
| `path=[object File]` in an upload request | argument order: `upload(files, path)` vs `uploadInsight(path, files)` |
| Requests unauthenticated inside an iframe | `waitForEmbedAuth()` not awaited before `initialize()` |
| Data loads twice on mount in dev (React) | StrictMode double-mount with `destroyOnUnmount` true - expected |
| Cards render `--` with a clean console | an empty `catch` around the pixel wrapper |

## Do not

- Do not reach for React to use this SDK. The core entry is complete on its own.
- Do not create more than one `Insight` for the app.
- Do not read or write `insight._store`.
- Do not hand-write the `semoss-env` tag or hardcode an app id in source.
- Do not run pixels before `isReady`, or without an `insightId`.
- Do not set `Content-Type` on an upload.
- Do not commit `.env.local`.
- Do not run `npm`, `pnpm`, or `node` to build - use `BuildAndPublishApp`.
